# Phase M — Activity inbox

Phase M improves the existing signed-in CampusGigs notification inbox. It does not enable payments or external push delivery.

- `All`, `Unread` and `Archived` views; latest 50 alerts per view.
- Unread bell counts exclude archived items, even when they were unread at archive time.
- Each account can read, archive or restore only its own alerts; archive is reversible and actions are idempotent.
- `Mark all read` affects only non-archived alerts.
- A repeat follow moves its original, deduplicated alert back to the inbox.
- An in-app toast appears for a newly observed unread alert while the member has the site open, without asking for notification permission. The first load is silent, and it auto-dismisses.
- Follows, service requests, booking decisions and provider reviews continue to be generated by the existing database triggers.

## API

- `GET /v1/me/notifications[?filter=all|unread|archived]` returns scoped alerts plus `unreadCount` and `archivedCount`.
- `POST /v1/me/notifications/:id/read`
- `POST /v1/me/notifications/:id/archive`
- `POST /v1/me/notifications/:id/restore`
- `POST /v1/me/notifications/read-all`

All routes require a verified member token. Archive/restore deliberately preserve records; the owner can recover them. Query filters reject unexpected parameters.

## Database release

Back up the production D1 database, then apply `apps/api/migrations/0012_phase_m_notifications.sql` before deploying the updated Worker. The migration adds a nullable `archived_at` column, an account-scoped index, and updates the follow trigger so a second follow reactivates an archived alert. No existing notification is removed.

## Verification

Run `npm run check`, `npm run test -w @campusgigs/api`, and `npm run build`. The Phase M test covers filter validation, user isolation, unread/archive totals, idempotency, restore, and repeat follow behavior.
